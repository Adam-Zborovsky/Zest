# M10 — Home-bar inventory and shopping list

Status: implemented and independently reviewed on 2026-09-14. The final clean checks are 493 Flutter tests and 66 backend tests; see [reviews/M10.md](reviews/M10.md).

## Product boundary

M10 turns the existing session-only bar matcher into a persistent home bar. A person records generic recipe ingredients they currently own, sees which locally cataloged recipes those ingredients can make, and keeps a short shopping list for missing essentials.

The milestone includes:

- A persistent binary inventory: an ingredient is either stocked or not stocked. Inventory uses the same normalized identities as recipe matching.
- Catalog-backed ingredient search. A person selects identities present in the on-device recipe catalog; M10 does not create free-form ingredients that cannot match a recipe.
- Matching the locally loaded recipe catalog into ready, substitution possible, and missing essentials using the existing reviewed M4 rules. The screen states the current catalog coverage and never implies completeness beyond recipes loaded on this device.
- A shopping list that accepts catalog ingredients manually and missing essential ingredients from a recipe or match result.
- Moving a shopping item to the bar in one action. Moving a stocked item to shopping represents running out.
- Offline-first storage and account sync for both stocked and shopping items.
- Loading, empty, offline, failed, narrow-width, large-text, keyboard, screen-reader, and reduced-motion treatment consistent with the rest of Zest.

M10 does not include quantities, bottle brands, prices, shops, expiry dates, barcode or label scanning, purchase history, party planning, automatic ordering, shared bars, custom ingredients, or a ranked “buy next” recommendation. Optional garnishes are not added automatically; a person may add their catalog identity manually.

## Interaction contract

`/bar` becomes the persistent home-bar entry point. The existing home action continues to open it. The screen has two explicit destinations:

- **My bar:** stocked ingredients, catalog search/add, and recipe matches.
- **Shopping:** ingredients to buy, manual catalog search/add, and “Added to bar” actions.

`/bar/shopping` is a real route so Back, browser history, and deep links behave predictably. The two destinations use Zest controls and route state rather than a gesture-only tab interaction.

When `/bar` is opened from a discovery result set, that explicit recipe scope remains in effect for the current session while availability still comes from the persistent stocked inventory. M10 never asks for a second session-only ingredient selection. A direct visit uses every full recipe stored in the local catalog. Copy identifies which scope is being matched and reports catalog coverage.

Adding an already-known ingredient is idempotent. Adding a shopping ingredient that is stocked moves it to shopping; adding a stocked ingredient that is shopping moves it to the bar. Removing an item hides it but preserves a tombstone for sync. A later explicit add has a newer timestamp and may restore it.

Recipe and match-result actions add only currently missing essential identities. Reviewed substitutions remain suggestions; Zest does not silently add or replace the source ingredient. Duplicate identities collapse to one item.

## Data model

One `HomeBarItem` exists per normalized ingredient identity:

| Field | Meaning |
| --- | --- |
| `ingredientId` | The deterministic `normalizeIngredientName` result; primary identity across devices. |
| `displayName` | The catalog spelling selected for display. It is user data once saved and travels with the record. |
| `location` | `stocked` or `shopping`. |
| `updatedAt` | UTC millisecond timestamp used by last-edit-wins. |
| `deleted` | Tombstone; later explicit writes may restore the item. |
| `revision` | Server-assigned per-user home-bar revision; absent from client PUT bodies. |

Local Drift rows also carry `dirty`. Local writes stamp `max(now, previous + 1 ms)`. The item key is the normalized identity rather than a random UUID, so adding the same ingredient independently on two devices converges to one record.

The existing `CollectionDatabase` receives the home-bar item and sync-state tables in schema 5. Its name is accepted technical debt: it is already the account-owned personal-data database, and renaming or introducing a second database adds migration and lifecycle risk without improving M10 behavior.

The catalog database remains provider-derived and separate. It supplies ingredient choices, full recipes, and coverage but stores no personal state.

## Backend and wire contract

The backend adds a `bar_items` table keyed by `(user_id, ingredient_id)` and a separate monotonic `bar_revision` counter on the user. Collection-entry revisions and home-bar revisions remain separate streams so an update in one stream cannot create gaps in the other's cursor.

Authenticated endpoints:

```text
GET /api/sync/bar-items?since=<revision>&limit=<optional>
PUT /api/bar-items/:ingredientId
```

The GET response is:

```json
{
  "items": [],
  "revision": 0,
  "hasMore": false
}
```

The PUT body contains `ingredientId`, `displayName`, `location`, `updatedAt`, and `deleted`. The decoded route identity must equal the body identity. Validation rejects blank or non-normalized identities, unknown fields, invalid locations, invalid timestamps, and oversized names or bodies. Limits are documented in the backend contract rather than inferred by clients.

Every accepted mutation locks the user row, increments `bar_revision`, and records the assigned revision. An incoming timestamp strictly later than the stored timestamp wins. Equal or earlier writes return the stored record unchanged. Unlike collection deletion, a home-bar tombstone is not permanent: a later explicit add restores it. User ownership is enforced on every query.

## Sync contract

A `HomeBarSyncEngine` mirrors the proven M8 sequence for this smaller record type:

1. Resolve local ownership. First account claims existing local items; a different account wipes them before pulling.
2. Push dirty records in deterministic ingredient order.
3. On an equal-timestamp content mismatch, restamp one millisecond later and retry once. Never clear `dirty` for a write the server did not accept.
4. Pull pages until caught up, applying a server record only when it is newer than a dirty local edit. Clean rows accept the server record, including ties.
5. Advance the home-bar revision cursor only after applying the page.

The app exposes one account-sync status in the profile sheet. A coordinator runs collection and home-bar sync together on launch, explicit “Sync now,” debounced local writes, and the final pre-sign-out push. Offline or failed status in either child sync is reflected in the combined status. One child failing does not erase dirty state in the other.

## Presentation direction

M10 uses the composed-design path approved by Adam: Zest’s existing design tokens and widgets, then review through layout, accessibility, writing, typography, color, and UI skills. Stitch remains available but is not used for this milestone.

The visual signature is a compact botanical shelf: stocked ingredient tags sit on quiet illustrated shelf rules, while match counts update below. It must remain a real semantic list and usable without decoration. Shopping uses the same ingredient vocabulary and a paper-checklist treatment; it does not imitate an ecommerce cart.

The interface reuses `NightBand`, `BotanicalPaper`, `PaperTag`, `ZestCard`, and existing match cards where they fit. It does not introduce a new palette, font family, navigation model, generic dashboard cards, or decorative motion. Any motion is brief, interruptible, and absent under reduced motion.

## Agent ownership

- **Backend agent:** Drizzle schema/migration, validation, repository, routes, backend contract types, and backend tests. No Flutter or product-document edits.
- **Flutter data agent:** home-bar domain model, Drift schema 5 and generated code, repository, sync API/engine, Riverpod data providers, and focused unit/data/sync tests. No presentation, router, `main.dart`, or backend edits.
- **Flutter UI agent:** `/bar` and `/bar/shopping` presentation, catalog search/match application state, actions from recipe/match surfaces, widget tests, semantics tests, and goldens. It codes against the model/provider contract in this document and does not edit Drift, sync, backend, router, or `main.dart`.
- **Integrator:** shared app wiring, router, main sync coordinator, conflict resolution, documentation, full checks, rendered review, and final independent review dispatch.

Agents do not commit. The integrator will review and assemble their changes before any M10 commit is proposed.

## Acceptance

- Inventory changes survive restart and work offline.
- The same normalized ingredient cannot appear twice or in both lists.
- Direct bar matching uses the local catalog; discovery-scoped matching still works and states its scope.
- Ready, substitution, missing, and optional-garnish behavior remains consistent with M4.
- Missing essentials can be added to shopping without adding optional garnishes or silently choosing substitutions.
- “Added to bar” removes an item from shopping and immediately updates recipe matches.
- Two-device sync converges across add, move, remove, restore, tied timestamps, offline edits, account changes, pagination, and session expiry.
- Backend tests prove authentication isolation, validation, revision paging, last-edit-wins, tombstones, and restoration.
- Flutter tests cover repository behavior, schema migration, sync conflicts, routing, empty/loading/error states, keyboard and semantics, 320-pixel width at 2x text, and reduced motion.
- Provider-derived ingredient/recipe surfaces retain TheCocktailDB attribution and source navigation.
- `flutter analyze`, `flutter test`, `npm run typecheck`, `npm test`, and `npm run build` are clean.
