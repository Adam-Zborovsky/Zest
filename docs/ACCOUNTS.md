# Accounts and synced collection (M8)

M8 gives Zest real accounts and stores each person's saved drinks, calendar days, variations, and memory photos on Zest's own backend, keyed by user ID. The app stays usable offline: the on-device collection database is a cache that syncs both ways. This document is the build contract for the M8 tracks and becomes the feature record once M8 closes.

## Decisions (Adam, 2026-09-13)

- **Own backend.** Extend the Fastify service in `backend/`. Supabase and Firebase were considered and declined.
- **Account required.** Login is email and password. "Continue on this device" is removed.
- **Offline-first sync.** The drift collection database remains the app's store. Local changes sync when the server is reachable. The last edit wins per entry.
- **Existing device data uploads** to the first account that signs in on that device.
- **PostgreSQL 18 with Drizzle ORM.** Postgres runs in Docker Compose on the development PC.
- **Photos on the server's disk,** readable only by their owner. There is no third-party object storage.
- **Local first.** The server runs on Adam's PC. A phone reaches it over the Wi-Fi LAN address. Deployment, HTTPS, and backups are a later milestone.
- **Email deferred.** There is no password reset or email verification. This is a known gap that must be closed before any deployment.
- **Sessions (integrator decision).** Opaque random bearer tokens. The server stores only a SHA-256 hash, and each device can log out on its own.

Supersedes: the M7 local-profile login (`docs/ONBOARDING.md`), and the `AGENTS.md` rule of no Docker, backend database, or accounts. `docs/PRODUCT.md` is updated at closeout.

## Wire contract

Every body is JSON with camelCase fields, unless stated otherwise. Errors keep the gateway's existing shape, `{ "error": { "code": "…", "message": "…" } }`, and never include stack traces, SQL, file paths, tokens, or passwords. Synthetic examples live in `contract/accounts/`; both test suites parse them.

### Validation shared by client and server

- **Email.** Trim, then lowercase. At most 254 characters, exactly one `@` with non-empty text on both sides, and no whitespace. The normalized form is what gets stored and compared.
- **Password.** 10 to 128 Unicode code points. No composition rules, per NIST SP 800-63B.
- **Entry id.** `^[0-9a-f]{32}$`, generated by the client (`newCollectionEntryId`). The server scopes it by user: the primary key is `(user_id, id)`.
- **`sourceRecipeId`:** `^[0-9]{1,20}$`. **`day`:** `YYYY-MM-DD` and a real calendar date.
- **`source`.** A JSON object, the `Recipe.toJson()` snapshot. The server treats it as opaque and caps it at 64 KiB serialized.
- **`variation`.** `{ name, ingredients: [{ name, measure }], method, notes }`, with the limits of `VariationDetails` and `VariationIngredient`: name ≤120, at most 30 ingredients, ingredient name ≤120, measure ≤80, method ≤8000, notes ≤4000, all trimmed. It is present exactly when `kind` is `variation` and the entry is not deleted.
- **Timestamps.** ISO-8601 in UTC. The server rejects an `updatedAt` more than 24 hours ahead of its own clock (`400 invalid_request`), so a bad clock cannot win every future conflict.

### Auth

| Route | Auth | Success | Failures |
| --- | --- | --- | --- |
| `POST /api/auth/register` `{ email, password }` | none | `201 { user, session }` | `400 invalid_request`, `409 email_taken`, `429 rate_limited` |
| `POST /api/auth/login` `{ email, password }` | none | `200 { user, session }` | `400`, `401 invalid_credentials`, `429` |
| `POST /api/auth/logout` | bearer | `204`; revokes only this session | `401 unauthorized` |
| `GET /api/auth/me` | bearer | `200 { user }` | `401` |

- `user` is `{ id, email, createdAt }`, where `id` is a UUID. `session` is `{ token, expiresAt }`.
- **Tokens.** 32 random bytes, base64url-encoded, sent as `Authorization: Bearer <token>`. The server stores only the SHA-256 hex digest. Expiry is 30 days from sign-in, with no sliding renewal. `last_used_at` is written at most once per hour.
- **Unknown sessions.** An unknown, expired, or revoked token gets `401 unauthorized` on every protected route.
- **Passwords.** Hashed with Argon2id. Production parameters are memory 19456 KiB, time 2, parallelism 1 (the OWASP minimum). Tests may inject cheaper parameters.
- **Unknown email.** Login verifies the password against a fixed dummy hash, so response time does not reveal whether the account exists. Both failure causes return the same `401 invalid_credentials` message.
- **Registration and enumeration.** Registration reveals `email_taken`. This is an accepted enumeration trade-off for a local, account-required app; it must be revisited before deployment.
- **Rate limits.**
  - Login: 10 per 15 minutes per IP, and 5 per 15 minutes per normalized email.
  - Registration: 5 per hour per IP.
  - Everything: 300 per minute per IP.
  - A limited request gets `429 rate_limited` with `Retry-After`.

### Entries and sync

`EntryRecord`:

```json
{
  "id": "…32 hex…",
  "kind": "saved | variation",
  "sourceRecipeId": "98001",
  "source": { },
  "variation": null,
  "day": "2026-09-13",
  "hasPhoto": false,
  "photoUpdatedAt": null,
  "createdAt": "…Z",
  "updatedAt": "…Z",
  "deleted": false,
  "revision": 12
}
```

A tombstone (`deleted: true`) keeps `id`, `kind`, `sourceRecipeId`, `day`, `createdAt`, and `updatedAt`. It sets `source` and `variation` to `null`, `hasPhoto` to `false`, and `photoUpdatedAt` to `null`.

On an entry PUT, the server ignores the client's `hasPhoto`, `photoUpdatedAt`, and `createdAt`: photo state changes only through the photo routes, the first `createdAt` is kept for the life of the entry, and clearing a photo stamps `photoUpdatedAt` with the request's `updatedAt` (not `null`).

| Route | Body | Result |
| --- | --- | --- |
| `GET /api/sync/entries?since=<int≥0>&limit=<1..500, default 200>` | none | `200 { entries: [EntryRecord], revision, hasMore }` |
| `PUT /api/entries/:id` | `EntryRecord` without `revision`; `id` must match the path | `200 EntryRecord`, the stored result |
| `PUT /api/entries/:id/photo?updatedAt=<iso>` | raw bytes, `Content-Type` of `image/jpeg`, `image/png`, or `image/webp`, at most 4 MiB | `200 EntryRecord` |
| `DELETE /api/entries/:id/photo?updatedAt=<iso>` | none | `200 EntryRecord` |
| `GET /api/entries/:id/photo` | none | `200` with the image bytes, their `Content-Type`, and `Cache-Control: private, no-store` |

All entry and sync routes require a bearer token, and every query filters by the token's user. An entry that does not exist, belongs to someone else, or is deleted gets `404 not_found`, never `403`. The server does not reveal that another user's id exists.

Sync rules:

1. **Revisions.**
   - Each user has a revision counter (`users.revision`). Every change to one of that user's entries (upsert, tombstone, photo set or clear) runs in one transaction that locks the user row (`SELECT … FOR UPDATE`), increments the counter, and stamps the entry with the new value.
   - Because of the lock, commit order equals revision order, so a pull by `since` never skips a change.
   - Pull returns the entries with `revision > since`, in ascending revision order, up to `limit`. The response `revision` is the last revision included, or `since` when there are none.
2. **Last edit wins.**
   - `PUT` applies when the incoming `updatedAt` is later than the stored `updatedAt`, or when no row exists.
   - An equal or earlier incoming value leaves the row unchanged, which makes retries idempotent.
   - The response is always the stored record after the operation. A client that loses adopts the server's version.
3. **Tombstones are final.** Once an entry is deleted, a later non-deleted `PUT` returns the tombstone unchanged, so a stale device cannot bring a deleted drink back. Deleting removes the photo file.
4. **Photos.**
   - Photo writes win on `photoUpdatedAt` in the same way.
   - The server checks magic bytes: the sniffed type must match `Content-Type`, otherwise `415 unsupported_media_type`.
   - A body over 4 MiB gets `413 payload_too_large`.
   - Files are stored at `PHOTO_DIR/<userId>/<entryId>`, and both path parts come only from validated ids. Writes go to a temporary file first and are then renamed.
   - A set or clear bumps the entry's revision and updates `hasPhoto` and `photoUpdatedAt`, so other devices re-fetch the photo.
   - Each user has a 512 MiB photo quota. Past it: `413 quota_exceeded`.

### Configuration and access

- **New backend variables.**
  - `DATABASE_URL` is required.
  - `PHOTO_DIR` defaults to `./data/photos` and is ignored by git.
  - `HOST` defaults to `127.0.0.1`. Set it to `0.0.0.0` to accept connections from the LAN.
  - `.env.example` documents the local Compose credentials. They are non-secret development values.
- **LAN warning.** Binding to the LAN also exposes the recipe gateway to every device on that network. The README says so.
- **CORS.** Origins stay loopback-only. Allowed methods become GET, POST, PUT, DELETE; allowed headers become Accept, Authorization, Content-Type. Credentials stay off. Native apps send no `Origin` header.
- **Flutter server URL.** Flutter keeps the single `ZEST_API_BASE_URL` define. The account and sync base is that URL resolved against `../` (for example, `http://192.168.1.20:3000/api/cocktails/` becomes `http://192.168.1.20:3000/api/`).
- **Allowed Flutter schemes.** Validation now also allows plain HTTP to private IPv4 hosts (10/8, 172.16/12, 192.168/16) as well as loopback. Android debug builds allow cleartext traffic through `android/app/src/debug/AndroidManifest.xml` only.

## Client behavior

- **Launch.**
  - `main()` loads the stored account and token before `runApp`. The account JSON is kept in `shared_preferences`, which is not secret; the token is kept in `flutter_secure_storage`.
  - "Signed in" means an account and a token are both present.
  - The onboarding flags and the launch-state table from M7 are unchanged.
- **Expired session.** Any authenticated call that gets `401` calls `AccountRepository.expireSession()`. The redirect then moves the person to login. Local data is kept.
- **Local schema 3.**
  - Entries gain `dirty` (default true), `deleted` (default false), and `photoDirty` (default false).
  - A `sync_state` table holds `ownerUserId` and `lastRevision`.
  - Existing rows migrate as dirty, so the first sign-in uploads them.
  - Reads hide deleted rows.
  - `delete` writes a tombstone and removes the photo bytes.
  - Every local write marks the row dirty. Photo writes also mark `photoDirty`.
  - `createdAt`, `updatedAt`, and the photo's `updatedAt` are stored as UTC milliseconds (schema 4), not Drift's default whole-second precision, so two edits inside the same second stay distinguishable to the server's last-edit-wins rule. Every write that bumps one of these columns sets `max(now, previous + 1ms)`, so it strictly advances even when the clock reads the same instant twice (or moves backwards).
- **Ownership.**
  - On sign-in with no `ownerUserId`, the device's data is claimed by that account and uploaded.
  - On sign-in as a different user than `ownerUserId`, the collection cache is cleared first. This includes unsynced rows; the sign-out step pushes first to minimize that loss.
  - Sign-out attempts one final push, then keeps the cache for that owner.
- **Sync pass** (`CollectionSync.syncNow`):
  1. Push dirty entries.
  2. Push photo changes.
  3. Pull pages until `hasMore` is false, then apply the results by the same last-edit-wins rule.
  4. Clear the dirty flags only for records the server returned as applied.

  The pass runs on sign-in, at app start, after local writes (debounced by 2 seconds), and from "Sync now". Status is exposed as `SyncStatus` (idle, syncing, offline, failed) for the profile sheet. It never blocks the collection screens.
  - **Push ties.** A push whose returned record ties the sent `updatedAt` (or `photoUpdatedAt`) but carries different content is a server-side rejection, not a success: the client leaves it dirty, re-stamps its local `updatedAt` strictly past what was sent, and retries once in the same pass before giving up to the next pass, instead of adopting the foreign record and clearing `dirty`. Nothing bounds a clock running backwards: last-edit-wins orders by the timestamps devices assign, not by when the edits actually happened, so concurrent edits from devices with wrong clocks resolve deterministically but not necessarily in human order.
