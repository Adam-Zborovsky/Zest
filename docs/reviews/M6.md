# M6 independent review — Collection, variations, memory photo

**Date:** 2026-09-13
**Reviewer:** a fresh Sonnet 5 subagent, read-only, with no part in building M6.
**Scope:** commits `4bc4087..e5d6d29`. That covers the M6 contract, the drift collection storage, the `image_picker` photo picker, the collection screens, the gateway "None Found" 502 fix, and the M6 documentation.
**Verdict:** APPROVE WITH FIXES. All four ROADMAP M6 acceptance criteria were met. One major and four minor findings were raised; all were resolved before closeout.

## Acceptance criteria

| Criterion | Reviewer finding | Evidence |
| --- | --- | --- |
| CRUD tested | Met | A shared contract suite runs against both the drift and in-memory repositories, plus drift-specific tests for the unique saved entry, malformed stored JSON, and a reopened database. |
| Photos never touch the repository, a server, or any cloud | Met | The picker makes no network calls, photos are stored only in the on-device `collection` database, and there is no upload or export code. |
| Variations clearly separate from source | Met | Variations are full independent copies, always labeled "Your variation of <source>", use a neutral ingredient marker, and never modify the source snapshot. |
| Export and backup not silently implemented | Met | No export or backup code exists; `docs/COLLECTION.md` lists it as out of scope. |

## Findings and resolutions

| # | Severity | Finding | Resolution |
| --- | --- | --- | --- |
| 1 | Major | Storage failures were silently dropped. Save and remove on recipe detail, entry delete, photo removal, storing a picked photo, and variation save caught no generic errors, so a failed save looked like a success. | Fixed. Each action now catches the failure and states it inline with `ZestInlineError` (icon plus plain copy, announced as a live region) while keeping the person on the same screen; the variation editor keeps the edits. `collection_failure_test.dart` covers save, delete, photo removal, and variation save, including recovery after a successful retry. |
| 2 | Minor | The back button tooltip read "Back to discovery" on collection pages, where the previous page may be anything. | Fixed. The tooltip is now "Back" everywhere; the five tests that located the button by the old text were updated. |
| 3 | Minor | The collection button pushed `/collection` even from inside the collection, stacking duplicate pages. | Fixed. Inside the collection it returns to the single list; elsewhere it still pushes so Back returns. A test taps it twice on the list and confirms one page with nothing to pop. |
| 4 | Minor | Android lost-photo recovery is not wired. | Accepted as a documented limitation. Correct recovery needs the pending entry id to survive process death, which needs a small persisted record; it is deferred rather than wired half-way. |
| 5 | Minor | `docs/COLLECTION.md` contradicted itself, saying the screens call `recoverLostPhoto()`. | Fixed. The photo-track note now says the method exists but is not called yet and points to the limitation. |
| 6 | Nit | No test of concurrent saves of the same recipe. | Added to the shared contract suite: three simultaneous `saveRecipe` calls produce one entry. It passes against both repositories. |
| 7 | Note | The drift repository's `photo()` would throw if a stored blob ever failed `MemoryPhoto` validation, instead of returning a fallback. | Recorded, not changed. It is unreachable today because the picker enforces the same limits before storage; revisit if storage ever accepts photos from another path. |
