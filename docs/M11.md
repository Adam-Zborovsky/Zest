# M11 — Shared catalog and search suggestions

Status: plan approved by Adam on 2026-09-14. The update behavior below is the approved "automatic on launch" variant. The build uses Sonnet subagents per track plus an independent Opus review. The UI follows the composed-skills path over the existing Botanical Play system.

## Why

Search is the weakest part of Zest. Four text inputs work four different ways:

| Surface | Today |
| --- | --- |
| Discover, by name | Submit-only `search.php?s=` through the gateway. No suggestions; needs the network; provider-defined matching. |
| Discover, by ingredient | Submit-only `filter.php?i=`. The person must guess the provider's exact ingredient spelling. |
| Constellation search | Local substring filter over loaded graph nodes; limited to loaded letters. |
| Home-bar picker | Local substring filter over loaded catalog ingredients. |

The data is small (the provider states 636 drinks and 489 ingredients), so ranking a few thousand strings per keystroke on-device is trivial. The real problems are that every device builds its own catalog through 26 paced letter browses (about a minute, pausable, failure-prone), every install repeats those provider calls, and nothing shares one matching and ranking rule.

## Decision (Adam, 2026-09-14)

Option B from the search analysis:

- The backend owns one shared catalog for all users, refreshed from TheCocktailDB's official endpoints. It is public catalog data, not per-user data.
- Clients download a versioned snapshot into the existing on-device catalog database and search it locally. Search stays fast and offline.
- Discover name, ingredient and letter results come from the local catalog instead of per-query provider calls.
- Suggestions appear in Discover, constellation search, the home-bar picker, and the variation editor's ingredient-name field (free text still allowed there).
- Adam accepts the risk of persisting provider-derived recipe records on Zest's server (recorded in `SOURCES.md`). Images are never mirrored.
- The app tells people when the catalog has been updated and applies updates on launch where possible.

Per-keystroke server search was rejected: it adds latency to typing, breaks offline-first behavior, and buys nothing at this data size.

## Backend

### Storage (Drizzle migration 0002)

| Table | Contents |
| --- | --- |
| `catalog_recipes` | `provider_id` (text PK), `name`, `source` (the validated provider record, text), `updated_at`. |
| `catalog_state` | Single row: `version` (SHA-256 of the canonical snapshot body), `recipe_count`, `published_at`, `checked_at`, `last_error_code`. |

### Refresh job

- Runs on startup when there is no published snapshot, the last check recorded a failure (`last_error_code` non-null — a crash or restart right after a failed run must not wait out the rest of a 24h interval), or `checked_at` is older than 24 hours. After a successful or unchanged check it reschedules 24 hours out. It uses `RecipeGateway` for the 26 `search.php?f=` letter browses, with a polite pause between them, and respects the existing 429 cooldown.
- **Retry on failure.** Scheduling is a single self-rescheduling timer, never a fixed interval, so the 24h success cadence and a failure retry can't double-fire. A failed run schedules a retry with bounded exponential backoff (5 min → 10 → 20 → … , capped at the 24h interval); a gateway `retryAfter` (seconds, e.g. from a 429) overrides the computed backoff when it is longer. A success or unchanged check resets the backoff.
- **All or nothing.** A new version is published only when all 26 letters succeed and validate. Recipes are deduplicated by provider id, and the swap happens in one transaction. A partial or failed run keeps the previous snapshot and records only an error code.
- If the canonical body hash matches the current version, only `checked_at` moves, so clients never see a false "updated".
- Injectable clock, fetcher, timers and pause/backoff values. Tests use PGlite and a fake fetcher, never the network.
- Provider keys and URLs are never logged, matching the gateway.

### Endpoint

`GET /api/catalog`: unauthenticated like the recipe gateway, and rate-limited.

- The body contains `version`, `publishedAt`, `recipeCount`, `attribution`, and `drinks` (provider-shaped records).
- It sets a strong `ETag` equal to `version` and answers `If-None-Match` with `304` when the current version matches any tag in it — a comma-separated list, weak `W/"..."` validators, and `*` are all accepted, per RFC 9110's weak-comparison rule for this header. `Cache-Control: no-cache` replaces the global `no-store` for this route only.
- State and drinks are read as one consistent pair: if a publish lands between the state read and the recipes read, the read is retried once so a served body's `version` always matches its `drinks`.
- The response is gzip-compressed with `node:zlib` when the client accepts it, so no new dependency is needed. The body is serialized once per published version and held in memory.
- Returns `503 catalog_unavailable` before the first successful refresh.

### Gateway cleanup

Once the client stops calling `search.php?s=`, `filter.php` and `list.php`, those proxy routes become dead and are removed. `lookup.php` stays as a recipe-detail fallback: saved recipes can reference drinks that later leave the catalog. The refresh job keeps using `search.php?f=` internally.

## Client

### Catalog data (catalog schema 2)

- A migration replaces `letter_sync` with a single-row `catalog_snapshot` table (`version`, `publishedAt`, `recipeCount`, `appliedAt`). `recipes` and `ingredient_usages` are kept. The `firstLetter` column is dropped because it described browse provenance, which no longer exists.
- `CatalogRepository.applySnapshot(snapshot)` replaces all recipes and usages in one transaction and returns a `CatalogDiff`: added, removed and changed counts, plus added recipe names for the notice.
- The letter sync engine, `catalogLetterSourceProvider`, `catalogLetterGapProvider`, `letterRecipes()` and the letter coverage wording are removed. Coverage becomes "TheCocktailDB catalog, N recipes, updated <date>". Copy still does not claim provider completeness.
- `CatalogSnapshotClient` does a conditional GET with `If-None-Match`. It has its own response limit (8 MB decompressed), timeout, validation of every drink record (the same rules as the gateway envelope), and typed errors for offline, unavailable and invalid responses.

### Update behavior

`CatalogUpdateController` (Riverpod notifier) states: `idle`, `checking`, `downloading`, `upToDate`, `updated(diff)`, `staged(diff)`, `failed(kind)`.

| Moment | Behavior |
| --- | --- |
| First launch, empty catalog | Download and apply automatically. The home card shows progress in place of today's "Start sync" card. Offline or failure shows the branded error with Retry. |
| Launch, local catalog exists | Check in the background after first frame. If there's a new version, download and apply it automatically, then show a notice: "Catalog updated · 4 new recipes". It's announced to screen readers and dismissable. |
| App resumed after 6+ hours | Check and download in the background, but do not swap data under the person. Show a notice with an **Update** action. Tapping applies it; otherwise it applies automatically at next launch. |
| Manual | "Check for catalog updates" in the profile sheet, reporting up to date, updated, or failed. |
| Failure with an existing catalog | Silent apart from the profile sheet status. The existing catalog keeps working offline. |

A notice appears only when a version actually changes, never for a `304` or a no-op. The diff wording only states counts it measured.

### Search index and ranking

`CatalogSearchIndex` is a pure Dart domain class built from the local catalog and rebuilt when the snapshot version changes.

- Entries: every recipe name, and every ingredient identity with its catalog display spellings and reviewed aliases (via `normalizeIngredientName`, so there's one normalization implementation).
- Folding: lowercase, whitespace collapse, Latin diacritic folding ("Crème de cassis" matches "creme"), and punctuation-insensitive matching.
- Ranking, first match wins: exact, prefix, word-prefix, substring, then one-edit typo tolerance for queries of 4+ characters. Ties go to ingredient prevalence (recipe count), then alphabetical. Results are capped per surface (8 for dropdowns).
- Tested as a unit with synthetic fixtures, including an adversarial-input and performance test over a 2,000-entry synthetic index.

### Shared suggestion field

`ZestSuggestionField<T>` is built on Flutter's `RawAutocomplete` (the documented widget for type-ahead from a local list), with a Botanical Play options view. Flutter has open issues with keyboard highlight and VoiceOver Full Keyboard Access for autocomplete options, so the component owns and tests:

- Up/Down to move, Enter to commit, and Escape to dismiss, with focus staying in the field.
- A strong highlighted-option state.
- An announced live-region count ("5 suggestions").
- Option semantics that include the kind ("Gin, ingredient").
- 48 px targets, 2× text, 320 px width, and reduced motion (no open animation).

## Frozen contracts between tracks

These are fixed so the backend, client-data and search-index tracks can build in parallel. Changing one needs the integrator's agreement.

### `GET /api/catalog` wire shape

```json
{
  "version": "<64 lowercase hex, sha256 of the canonical drinks JSON>",
  "publishedAt": "2026-09-14T08:00:00.000Z",
  "recipeCount": 636,
  "attribution": { "name": "TheCocktailDB", "url": "https://www.thecocktaildb.com" },
  "drinks": [ { "idDrink": "11007", "strDrink": "Margarita", "...": "provider fields verbatim" } ]
}
```

- `drinks` is sorted by `idDrink` numerically (as a decimal string compare by length, then lexically) and deduplicated by `idDrink`. `recipeCount === drinks.length`.
- The canonical JSON is `JSON.stringify(drinks)` after sorting, with each drink's keys in the order the provider returned them.
- Responses: `200` with `ETag: "<version>"` and `Cache-Control: no-cache`; `304` with an empty body when `If-None-Match` equals the quoted version; `503 {"error":{"code":"catalog_unavailable",...}}` before the first publish; `429` from the rate limiter with `Retry-After`.
- Gzip when `Accept-Encoding` includes `gzip` (`Content-Encoding: gzip`, `Vary: Accept-Encoding`).

### Catalog database (client, schema 2)

- Tables: `recipes(providerId PK, name, sourceJson, updatedAt)`, `ingredient_usages(recipeId, normalizedIngredient)`, and `catalog_snapshot(id PK = 1, version, publishedAt, recipeCount, appliedAt)`.
- The upgrade from 1 drops and recreates every catalog table. The catalog is re-downloadable provider data, not personal data.
- `CatalogRepository` keeps `allRecipes()`, `recipeCount()`, `ingredientPrevalence()` and `coverage()`, and adds `applySnapshot(CatalogSnapshot) → CatalogDiff`, `currentSnapshot() → CatalogSnapshotInfo?`, and `recipeById(String) → Recipe?`.

### Search index API (client, `lib/features/catalog/domain/catalog_search_index.dart`)

```dart
enum CatalogSuggestionKind { recipe, ingredient }

final class CatalogSuggestion {
  final CatalogSuggestionKind kind;
  final String id;      // provider id for recipes; normalized identity for ingredients
  final String label;   // display text (recipe name; most common catalog spelling for ingredients)
  final int recipeCount; // 1 for recipes; prevalence for ingredients
}

final class CatalogSearchIndex {
  factory CatalogSearchIndex.fromRecipes(Iterable<Recipe> recipes);
  static final CatalogSearchIndex empty = CatalogSearchIndex.fromRecipes(const []);
  List<CatalogSuggestion> suggest(String query, {Set<CatalogSuggestionKind> kinds = const {recipe, ingredient}, int limit = 8});
  List<String> recipeIdsMatchingName(String query);          // all ranked matches, no limit
  List<String> recipeIdsWithIngredient(String identity);     // exact normalized identity
}

String foldSearchText(String input);
```

## Acceptance

- A fresh install with the backend running has a full catalog and working suggestions within one snapshot download, with no 26-request client sync.
- An offline launch with an existing catalog: all search surfaces and suggestions work.
- A new server version triggers an automatic apply and a notice on launch, and a staged **Update** notice after resume. Unchanged versions produce no notice.
- A failed or partial server refresh never publishes, and clients keep the previous catalog.
- Typing "creme", "lime jiuce" or "old fash" yields the expected ranked suggestions; keyboard-only and screen-reader flows are tested.
- No provider records or images in the repository. Tests use synthetic fixtures only.
